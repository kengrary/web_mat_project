# 全链路系统集成设计：上传 → 队列解析 → Java API 服务 → Agent

> 落地形态：**Python 主控服务（上传/分块/队列/进度/已有 agent）+ 独立 Java MAT API 服务**。
> 已确认约束：仅 hprof｜内嵌 Equinox｜解析与查询分离｜Python↔Java 用 **REST/JSON**｜
> snapshot 缓存层与查询结果对象层**都用 Java SoftReference 分层管理**，防 Java 服务 OOM。
> 本文给出全链路集成设计；解析进程归属由本文权衡给出推荐。

---

## 0. 部署拓扑（确定方案）：Java 模块独立部署，Python 唯一入口
> heapdump 分析相关模块（解析 + 查询服务）整体放**独立云服务器 / 内网，无外网入口**；
> **Python 服务是唯一外网入口**，所有用户/前端请求都经它进来，再由它反代到内网 Java 服务。
>
> 推论（贯穿全文的硬约定）：
> - **Java 侧无鉴权、无 CORS、无外网** —— 安全靠网络隔离 + Python 唯一入口（Python 有鉴权/配额/权限）。
> - **前端不直连 Java 8090**，只调 Python 的 `/api/heapdump-reports/...`（同源，天然无 CORS）。
> - 查询服务 `MAT_QUERY_BIND` 绑**内网网卡 IP**（让 Python 跨机连得上，但不暴露公网）。
> - 安全双保险：① 安全组只放行 Python IP；② 绑定具体内网 IP（非 0.0.0.0）。
> 部署落地细节见 `query-service/DEPLOY.md`。

## 2. 解析进程归属 —— 推荐方案与理由

> 你让我权衡"解析由谁执行"。**推荐：Python 从队列取任务，为每个 dump fork 一个独立的 Java 解析子进程（CLI），与常驻的 Java Query API 服务分离。**

### 为什么解析要独立子进程，而不是塞进 Query API 服务

| 维度 | 独立解析子进程（推荐） | 塞进 Query API 服务 |
|---|---|---|
| 内存隔离 | 解析峰值内存（`N×28.25+C×1000`，可达数十 GB）随进程退出**彻底归还 OS** | 解析峰值会和在线查询抢内存，极易 OOM/GC 风暴 |
| 故障隔离 | 解析 OOM/崩溃只死一个子进程，不影响在线查询 | 一次解析失败可能拖垮整个 API 服务 |
| 资源调参 | 可单独给解析进程设大 `-Xmx`；Query 服务设小而稳 | 一套 JVM 参数难同时满足两种负载 |
| 顺序控制 | 天然契合"单解析服务器顺序处理" | 需在服务内加锁/限流 |
| 中断 | 直接 kill 子进程，干净利落 | 需 MAT 的 `IProgressListener.cancel` 协作式中断（不一定即时） |

### 谁来调度？
- **Python 持有队列与调度**（你已有的队列），保证全局**单并发**解析。
- Python 用 `subprocess` 启动 `java -jar mat-parser-cli.jar parse <hprof> <outDir>`，
  通过**子进程 stdout 的结构化进度行**（或写进度文件）回传进度给前端。
- 这样解析的"业务编排"在 Python（与已有体系一致），"重计算"在隔离的 Java 进程。

> 例外：若不想引入第二种 Java 制品，也可让 Query API 服务暴露一个 `/parse` 端点，
> 但**内部仍 fork 子进程**执行解析（服务只做转发+进度中继），保留内存隔离优势。

### 中断（cancel）的两段式
1. Python 收到前端中断 → 从队列移除/标记任务；若已在跑 → `terminate()` 解析子进程。
2. 清理该 dumpId 目录下**半成品 index**（解析未完成的 index 不可用，必须删，否则 reopen 会读到坏数据）。

## 3. 分块大文件上传（Python 侧）

heapdump 常达几 GB~几十 GB，必须分块。

### 协议（REST）
```
POST /uploads                      → 创建上传会话，返回 uploadId、chunkSize、已存在分块(断点续传)
PUT  /uploads/{uploadId}/chunks/{index}   (body=分块二进制, header: Content-MD5)
GET  /uploads/{uploadId}/status    → 已收哪些块（断点续传用）
POST /uploads/{uploadId}/complete  → 校验全量 → 合并 → 生成 dumpId → 入解析队列
DELETE /uploads/{uploadId}         → 取消上传
```

### 要点
- **分块大小**：8~16 MB（平衡请求数与重传成本）。
- **断点续传**：每块独立落盘 `<uploadId>/<index>.part`，complete 时按序合并；客户端可查 status 跳过已传块。
- **完整性**：每块 Content-MD5 校验；complete 时校验总大小 + 整体哈希。
- **流式落盘**：分块直接写磁盘，**不在内存累积**（Python 服务也要防 OOM）。
- **格式预检**：complete 后读前若干字节校验 hprof magic（`JAVA PROFILE 1.0.x`），早失败。
- **磁盘配额**：上传前检查剩余空间（hprof + index 约需 1.3~1.6× 原始大小）。

## 4. 任务队列与进度（Python 侧）

### 任务状态机
```
QUEUED → PARSING → DONE
   │        │        
   └─CANCELLED┘   └→ FAILED
```

### 任务记录（持久化，重启可恢复）
```jsonc
{
  "dumpId": "d-20260628-xxx",
  "filename": "app-oom.hprof",
  "sizeBytes": 8123456789,
  "status": "PARSING",
  "progress": 0.62,           // 0~1
  "phase": "DominatorTree",   // 来自解析子进程上报
  "queuedAt": ..., "startedAt": ..., "finishedAt": null,
  "indexDir": "/data/dumps/d-.../",
  "error": null
}
```

### 进度来源
- 解析子进程把 MAT 的 `IProgressListener` 进度（Pass1/Pass2/GC/DominatorTree 各阶段，见文档01权重 `{700,30,90,20,150,10}`）转成结构化行打到 stdout，Python 解析并更新任务进度。
- 前端：**SSE 优先**（实时推进度），降级为轮询 `GET /tasks/{dumpId}`。

### 单消费者
- 一个 worker 顺序消费队列；解析中可中断（§2）。
- 解析完成 → 任务置 DONE → 前端出现"类 MAT 功能菜单"（菜单项对应 Java Query API 的能力）。

## 6. 三层 SoftReference 内存管理（防 Java 服务 OOM）★ 本设计核心

> 关键认知（读 MAT 源码确认）：**MAT 内部已经在用 SoftReference 缓存 index 页**
> （`IndexReader`/`IndexWriter` 的 page cache），且 `SnapshotFactoryImpl` 的 snapshot 缓存用的是
> **WeakReference + 引用计数(usageCount) + 显式 dispose**。
> 所以我们的软引用设计**不能盲目再包一层**，要分清三层、各司其职，避免冲突。

### 层 A：MAT 内部 index 页缓存（已存在，不要重复造）
- 机制：每页 `SoftReference<ArrayIntCompressed>`，内存紧张时被 GC 回收，下次访问从磁盘重读。
- 我们要做的：**保证 hprof+index 文件常驻磁盘**（页能重读），并给 JVM 合理堆大小让软引用发挥作用。
- **不要**对 MAT 内部页再加缓存层。

### 层 B：SnapshotManager —— ISnapshot 缓存（我们实现，用 SoftReference + 引用计数）
这是"整个 dump 的入口对象"。设计：
```java
class SnapshotManager {
  // dumpId → 软引用持有的 snapshot 句柄
  Map<String, SoftReference<SnapshotHolder>> cache;

  class SnapshotHolder {
    ISnapshot snapshot;
    AtomicInteger inUse;        // 正在服务的请求数(引用计数)
    volatile long lastAccess;
    File hprof, indexDir;
  }

  ISnapshot acquire(dumpId) {
    holder = cache.get(dumpId)?.get();
    if (holder == null) {                 // 被 GC 回收或首次
      holder = openSnapshot(hprof);        // 重新打开(index 在 → 秒级)
      cache.put(dumpId, new SoftReference<>(holder));
    }
    holder.inUse.incrementAndGet();
    holder.lastAccess = now();
    return holder.snapshot;
  }
  void release(dumpId) { holder.inUse.decrementAndGet(); }
}
```
**要点 / 与 MAT 机制的协调**：
1. **SoftReference 让内存紧张时整个 snapshot 可被回收**——正是你要的"避免 OOM"。回收后下次 `acquire` 因 index 仍在磁盘 → `readFromFile` 秒级重建。
2. **引用计数防"正在用时被 dispose"**：`inUse>0` 期间，即便软引用被清，也要能从一个**临时强引用**保住正在服务的请求（用 try/finally 在请求作用域内持强引用，请求结束才放）。
3. **不要主动 `dispose()` 还在用的 snapshot**；空闲且 `inUse==0` 才允许被 GC 或 LRU 主动 dispose（dispose 会关 index 文件句柄）。
4. **SoftReference vs WeakReference 取舍**：snapshot 句柄用 **Soft**（尽量留住，加速复用），结果对象（层C）按大小可 Soft/Weak 混用。

### 层 C：查询结果对象缓存（我们实现，用 SoftReference）
单次查询可能产出大结果集（histogram 全量、retained set 几万 id）。
```java
// resultId → 软引用持有的结果(用于分页游标二次取、agent 复用)
Map<String, SoftReference<QueryResult>> resultCache;
```
**要点**：
1. 结果分页：首次算全量 → 软引用缓存 → 后续 `cursor` 翻页命中缓存；被回收则按需重算。
2. **大结果优先 Weak / 设上限**：超大结果（如百万级 id）不进缓存或只存"重算所需参数"，避免缓存本身撑爆堆。
3. 给每个结果加 `sizeHint`，配合一个**自管理 LRU + 软引用**：常规走 LRU 上限，越界后降级为纯软引用兜底。

### 整体内存策略
- **JVM 参数**：Query 服务 `-Xmx` 设为机器内存的 60~70%，留余量给 OS 文件缓存（index 页重读靠它）。
- **GC**：用 G1/ZGC；SoftReference 回收激进度可调（`-XX:SoftRefLRUPolicyMSPerMB`），内存吃紧机器调小。
- **兜底**：注册 `MemoryMXBean` 监听，逼近阈值时主动 dispose 空闲 snapshot（不等 GC）。
- **并发打开上限**：限制同时 `inUse>0` 的 dump 数（信号量），超限的请求排队，防止一次涌入多个大 dump 直接 OOM。

## 7. Python ↔ Java 协作流程（端到端）

### 解析流程
```
1. 前端分块上传 → Python complete → 生成 dumpId，写 /data/dumps/<dumpId>/app.hprof → 入队
2. Python worker 顺序取任务 → fork: java -jar parser-cli.jar parse app.hprof <dir>
3. 子进程 stdout 进度行 → Python 更新任务进度 → SSE 推前端
4. 完成 → 任务 DONE，目录含 app.hprof + *.index
5. 前端显示"类 MAT 菜单"
```

### 查询流程
```
1. 前端点菜单(如 Histogram) → Python Diagnose Proxy → 转发 GET java:/snapshots/<dumpId>/histogram
2. Java SnapshotManager.acquire(dumpId)(软引用缓存命中或秒级重开) → 执行 → 结果瘦身 → 返回
3. Python 透传/聚合给前端
```

### Agent 流程（接入已有 openai-sdk 手写 agent loop）
```
1. 用户自然语言 → Python agent loop
2. agent 的工具 = 对 Java /tools 端点的封装(原子+复合诊断，见文档04)
3. agent 思考→调工具(HTTP 到 Java)→看瘦身后的结果→再思考→结论
4. 与已有 gc日志/jstack 工具同处一个 agent 工具箱，可跨数据源联合诊断
   (例: jstack 看到线程阻塞 + heapdump 看到连接池打满 → 关联结论)
```
> 复用红利：你的 agent 已是手写 loop，新增 MAT 工具只是往工具箱里加几个 HTTP 调用封装，无需改框架。

## 8. 目录与存储约定

```
/data/
  uploads/<uploadId>/0.part 1.part ...        # 上传中的分块(合并后删)
  dumps/<dumpId>/
      app.hprof                                # 原始 dump(reopen 必需)
      app.idx.index app.o2c.index ...          # 全套 MAT index(分目录隔离)
      app.threads                              # 线程栈文本
      parse.log                                # 解析日志/进度归档
      meta.json                                # dumpId/原文件名/大小/解析参数/时间
```
- 每个 dump 一个独立目录 → 天然隔离、易清理、易整目录拷贝（解析机→查询机）。
- 清理策略：DONE 任务按 LRU/TTL 回收磁盘；删目录前确认 Java 服务已 close 该 snapshot（释放文件句柄）。

## 9. 失败与边界处理

| 场景 | 处理 |
|---|---|
| 上传中断 | 断点续传(status 查已传块)；超时未 complete 的 upload 定时清理 |
| 解析 OOM | 子进程退出码捕获(MAT 用 79)；任务 FAILED + 提示加大解析机内存/用 discard 抽样 |
| 解析中断 | kill 子进程 + 删半成品 index(否则 reopen 读坏数据) |
| 多 dump in one file | MAT 抛 MultipleSnapshotsException；Python 回传候选 id 让用户选 snapshot_identifier 重试 |
| Java 服务内存紧张 | 软引用层 C/B 依次被回收；MemoryMXBean 兜底主动 dispose；并发上限排队 |
| index 与 hprof 不匹配 | reopen 校验(hprof 改动则 index 失效需重解析)；按 dumpId 目录管理避免错配 |
| Java 服务重启 | snapshot 缓存丢失无妨——index 在磁盘，首次请求按需秒级重开 |
